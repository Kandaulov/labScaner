# labScaner — решения и открытые вопросы

Формат ADR: контекст → решение → последствия. Новое решение — новый номер; старое не удаляется,
а помечается «Заменено ADR-NNN».

---

## ADR-001. Backend: .NET 10 + ASP.NET Core
**Контекст.** Ранее рассматривался стек FastAPI + Celery + Redis. Преподаватель-владелец знает .NET и PostgreSQL
и будет сопровождать систему сам.
**Решение.** .NET 10 (LTS), ASP.NET Core, EF Core + Npgsql. Заменяет ранний вариант на Python.
**Последствия.** Один язык для всего; MailKit, OpenXml, PdfPig закрывают почту и документы.

## ADR-002. СУБД: PostgreSQL 17
**Решение.** PostgreSQL — и для данных, и для очереди фоновых задач.

## ADR-003. Фоновые задачи: Hangfire на PostgreSQL, без Redis
**Контекст.** Нагрузка маленькая (тысячи писем за семестр). Нужны: расписание, повторы, видимость ошибок.
**Решение.** Hangfire + Hangfire.PostgreSql внутри того же процесса.
**Последствия.** Меньше контейнеров; есть готовый dashboard задач. Redis не нужен.

## ADR-004. UI: Razor Pages + htmx, без React
**Контекст.** Пользователь один, экранов ~11, самый интерактивный — таблица журнала. React даёт отдельную
сборку, API-слой, дублирование моделей.
**Решение.** Server-side Razor Pages; интерактивность — htmx (частичные обновления: ячейка журнала,
карточка в боковой панели, сохранение без перезагрузки) и точечно Alpine.js.
**Последствия.** Один деплой, нет JS-сборки. Если журнал упрётся в возможности htmx, его можно
переписать «островом» на React без переделки остального — это будет отдельный ADR.

## ADR-006. Повторная сдача = новая версия
**Решение.** Файлы не перезаписываются; `Submission.version` растёт, актуальна последняя (`is_current`).
Новая версия сбрасывает статус ячейки на «Получено», прежние проверки и решения остаются в истории.

## ADR-007. ИИ — аудитор, не экзаменатор
**Решение.** LLM проверяет полноту разделов, выполнение чек-листа, согласованность чисел, уместность
решений и *предлагает* оценку. Оценку ставит преподаватель. Ничего не уходит студенту без подтверждения.
Итоговые оценки — только вручную (система может лишь *предложить* автомат, см. ADR-013).

## ADR-008. Обезличивание перед LLM
**Контекст.** ФИО, e-mail и работы студентов — персональные данные (152-ФЗ).
**Решение.** Перед отправкой в LLM из текста удаляются ФИО (по справочнику), e-mail, номер группы;
в запросе студент не идентифицируется.

## ADR-009. Развёртывание: Docker Compose + Caddy на VPS, CI/CD в GitHub Actions
**Решение.** Контейнеры `app`, `db`, `caddy`; образ в GHCR; деплой по тегу через ssh.

## ADR-010. Формат темы письма
**Решение (утверждено преподавателем).**
```
{Группа} – {Предмет} – {ФИО} – Лаб №{номер}
{Группа} – {Предмет} – {ФИО} – Курсовая
```
Примеры: `ИСТ-41 – КорпИС – Иванов Иван Иванович – Лаб №3`, `ИСТ-41 – КорпИС – Иванов И.И. – Курсовая`

Предметы (коды в теме): **КорпИС**, **ОС**, **СПП**. У предмета есть список допустимых написаний
(алиасов), регистр не важен.

Правила разбора:
- Разделитель — тире **с пробелами вокруг**: `–`, `—` или `-`. Пробелы обязательны, потому что
  дефис встречается внутри названия группы (`ИСТ-41`) и двойных фамилий.
- Префиксы `Re:`, `Fwd:`, `Fw:`, `[SPAM]` и т.п. отбрасываются; закодированные темы (`=?UTF-8?B?…?=`,
  `windows-1251`) декодируются.
- Работа: `Лаб №3`, `Лаб № 3`, `Лаб.3`, `Лаб 3`, `ЛР3`, `Лабораторная 3` → лабораторная №3;
  `Курсовая`, `КР`, `Курсовой проект` → курсовая.
- ФИО: полное или `Фамилия И.О.`; `ё = е`; ищется среди студентов указанной группы.
  Если не найдено или неоднозначно — по e-mail отправителя.
- Если части не удалось разобрать по разделителям — пробуем найти известные группу и предмет по словарю.
- Что не распознано — в «Нераспознанные», ручное сопоставление. Ничего не теряется.

## ADR-011. Хранилище: существующие папки преподавателя на Яндекс Диске
**Контекст.** Отчётные материалы уже хранятся в сложившейся структуре, например:
`30 Политех/03 КорпИС/10 КорпИС - Отчетные документы/2026-2027 КорпИС ИСТ - 7 сем`.
Папка приложения туда не дотягивается.
**Решение.**
- OAuth-приложение Яндекса с правами `cloud_api:disk.read` и `cloud_api:disk.write` (весь Диск).
- У каждого **предмета в семестре** (`SubjectTerm`) хранится **корневая папка** — полный путь на Диске.
  Система предлагает путь по шаблону предмета, преподаватель может поправить.
- Внутри корневой папки — по две папки на каждую группу (утверждено преподавателем):
  ```
  2026-2027 КорпИС ИСТ - 7 сем/
    ИСТ-41 - ЛР/
    ИСТ-41 - Кр/
    ИСТ-42 - ЛР/
    ИСТ-42 - Кр/
    Задания/            ← DOCX с заданиями (ADR-012)
  ```
- Имя файла внутри (утверждено, шаблон настраивается):
  `Лаб 03 - Иванов И.И. - v1.docx`, `Курсовая - Иванов И.И. - v1.docx`.
  Номер лабы с ведущим нулём — чтобы файлы сортировались по лабам. Исходное имя файла студента
  сохраняется в БД.
- Временная папка — `Приложения/LabScaner/_incoming/`.
- Недостающие папки создаются автоматически. Система ничего не удаляет и не перезаписывает.
**Последствия.** Широкие права на Диск → токен хранится зашифрованным, адаптер не имеет операций
удаления (проверяется тестом).

## ADR-012. Задания: один DOCX на все лабы + один DOCX на курсовую
**Контекст.** У каждого предмета свои лабы. Задания на все лабы предмета — в одном документе,
задание на курсовую — в отдельном.
**Решение.**
- Перечень работ (`Assignment`) принадлежит **предмету в семестре** (`SubjectTerm`): лабы могут меняться
  от года к году. Есть действие «скопировать из прошлого семестра».
- У предмета в семестре два файла-задания: «Задания на лабораторные» и «Задание на курсовую».
  Загружаются через интерфейс (или выбираются на Диске), хранятся в `{корень}/Задания/`.
- Документ с лабами система **делит по заголовкам** «Лабораторная работа №N» (стили Heading или
  жирный текст абзаца) и создаёт/обновляет работы ЛР1…ЛРn. Результат деления преподаватель видит
  и подтверждает: номер → название → начало текста. Если деление не удалось — можно поправить
  границы вручную.
- Извлечённый текст задания + чек-лист уходят в LLM при проверке.

## ADR-013. Дедлайны и автоматы
**Решение (правило утверждено преподавателем).**
- Учебный семестр (`Term`) хранит календарь: **начало зачётной недели** и **начало сессии**.
- Дедлайн: лабораторные — начало зачётной недели, курсовая — начало сессии; можно переопределить.
- **«В срок»** = преподаватель **принял** работу («лаба ОК») не позже дедлайна. Дата сдачи
  студентом сама по себе «в срок» не делает.
- **Претендент на автомат** = все лабораторные приняты до дедлайна лаб **и**, если в предмете есть курсовая,
  курсовая принята до дедлайна курсовой (начало сессии). Предмет может быть без курсовой — тогда
  учитываются только лабы.
- Автомат: для зачёта — «зачтено», для экзамена — «5 (отлично)». Для дифференцированного зачёта — «5».
- Выставляет автомат преподаватель (одной кнопкой для всех претендентов), не система.
- Так как срок зависит от скорости проверки, система **напоминает** о непроверенных работах:
  за 7 и за 2 дня до дедлайна в ленте «Что ждёт от меня» появляется задача
  «N работ сданы, но не приняты — дедлайн {дата}».

## ADR-014. LLM: Timeweb Cloud AI Gateway через OpenAI-совместимый API
**Контекст.** VPS размещается в России на Timeweb Cloud. У Timeweb есть AI Gateway — доступ к разным
моделям через единый API, в том числе OpenAI-совместимый; оплата в рамках того же аккаунта.
**Решение.**
- Одна реализация `ILlmClient` поверх OpenAI-совместимого API (Chat Completions). Base URL, ключ и модель —
  в настройках. По умолчанию — AI Gateway Timeweb.
- Модель выбирается в настройках; для сравнения моделей хранится `AiCheck.model` и `prompt_version`.
- Ответ модели — строго JSON по схеме; при невалидном JSON — одна повторная попытка, затем статус
  «ИИ не справился» и ручная проверка.
- Обезличивание (ADR-008) сохраняется: запрос может уходить к зарубежной модели через шлюз.
**Проверить на этапе 6:** какие модели реально доступны в Gateway, поддержка `response_format`/JSON schema,
лимит контекста (курсовые длинные), цена за проверку одной работы.

## ADR-015. Три журнала и управление приёмом почты
**Решение.** В интерфейсе три разных журнала:
1. **Журнал событий** — что система сделала и что ждёт от преподавателя. Две части: лента «Что ждёт
   от меня» (задачи: проверить работы, разобрать нераспознанные письма, подтвердить автоматы,
   отправить уведомления, исправить настройки) и полная лента событий с фильтрами.
2. **Журнал проверки работы** — ход обработки конкретной сдачи по шагам конвейера (получено →
   сохранено на Диск → текст извлечён → проверка ИИ → решение преподавателя → уведомление),
   с временем, длительностью, ошибками и кнопкой «Повторить шаг». Плюс общий список «Обработка»
   всех сдач в пути.
3. **Журнал группы** — оценки и отметки по лабораторным, курсовой, экзамену/зачёту, автоматам, плюс
   **история комментариев** по каждой лабе (замечания ИИ, замечания преподавателя, что отправлено
   студенту, пересдачи).

Приём почты: автоматический по расписанию (интервал в настройках, можно выключить) и кнопка
**«Проверить почту сейчас»** с показом результата (сколько писем, сколько распознано). Статус
приёма (последняя проверка, следующая, ошибка подключения) виден постоянно.

## ADR-016. Несколько преподавателей
**Контекст.** Системой могут пользоваться коллеги. У каждого свои предметы, своя почта для сдачи работ
и свой Яндекс Диск.
**Решение.**
- Пользователи: роли **Преподаватель** и **Администратор** (администратор — тоже преподаватель с
  доп. правами). Аутентификация — ASP.NET Core Identity (вход, блокировка после попыток, смена и сброс
  пароля администратором).
- **Принадлежат преподавателю:** предметы и всё под ними (семестры предмета, работы, сдачи, журналы,
  комментарии, уведомления), а также подключения: почтовый ящик (IMAP/SMTP), Яндекс Диск (OAuth-токен),
  шаблоны писем. Преподаватель видит только своё.
- **Общие для системы:** группы и студенты, учебный календарь (зачётная неделя, сессия), настройки LLM
  (адрес Gateway, ключ, модель по умолчанию, лимиты) — ведёт администратор.
- Конвейер работает по каждому подключённому ящику отдельно; письмо из ящика преподавателя ищет предмет
  только среди его предметов. Коды предметов уникальны в пределах преподавателя.
- Все запросы к данным фильтруются по `teacher_id` (глобальный фильтр EF Core) — проверяется тестами.
**Последствия.** Немного больше работы на этапе 2 (Identity, роли, фильтр), зато не придётся
переделывать модель потом. Интерфейс администратора — простой: список преподавателей, общие настройки.
